Build the next major Sparki foundation sprint.

Goal:
Turn Sparki from a working frontend/app shell into a durable AI Performance Platform with persistent AI memory, real athlete context, privacy foundations, and a clear technical roadmap.

Do not build isolated UI features.
Do not add new decorative screens.
Prioritise backend/data flow, persistence, and product architecture.

Context from current audit:
- The v0 frontend migration is complete.
- Athlete profile, onboarding, roles, race calendar, race management, race phasing, recovery/sleep, lab insights and AI briefing mostly work.
- Database has several useful tables but almost all real usage data is near-zero.
- AI daily briefing and AI Q&A call a real LLM.
- Main weakness: AI outputs are not persisted.
- AI observations tables are currently dead/unused.
- Coach/parent relationships are stored but not surfaced.
- Integrations are placeholders.
- Nutrition, route planning, equipment advice, notifications and social/together training are mostly mock/static.
- Privacy/consent is incomplete.
- Onboarding completion currently lives in localStorage and should become persistent in DB.

Sprint name:
Sparki AI Memory & Core Data Foundation

Build scope:

PHASE 1 — Persistent AI Memory

Create a real persistent AI memory system.

Use or repair the existing ai_observations-related tables if they exist.
If the current schema is dead or unsuitable, safely migrate/extend it instead of creating duplicate concepts.

Create tables/entities for:

AIObservation:
- id
- athlete_id
- source_type: daily_briefing, ai_chat, training_analysis, recovery_analysis, race_analysis, nutrition_analysis, manual_note, system
- title
- summary
- observation_text
- confidence: low, medium, high
- category: training, recovery, race, nutrition, hydration, equipment, mental, planning, health, general
- severity: info, watch, important, urgent
- detected_pattern
- supporting_data_refs
- recommended_action
- status: new, acknowledged, saved, dismissed, outdated
- created_at
- updated_at
- expires_at nullable

AIMemoryEvent:
- id
- athlete_id
- event_type: briefing_generated, observation_created, user_acknowledged, user_dismissed, user_saved, model_updated, recommendation_followed
- related_observation_id nullable
- metadata json
- created_at

AIPreference:
- athlete_id
- communication_style: direct, supportive, analytical, concise, detailed
- coaching_intensity: low, normal, high
- explanation_level: simple, normal, expert
- sensitive_topics: json
- preferred_units
- created_at
- updated_at

Requirements:
- Store AI briefing outputs.
- Store AI observations.
- Store important AI Q&A outputs when useful.
- Never store everything blindly. Persist only structured summaries and useful observations.
- Add deduplication: do not save identical observations repeatedly.
- Add status handling: user can acknowledge, save or dismiss observations.
- Add a simple “AI Memory” or “Observations history” area in Lab.
- Show observations grouped by category and recency.
- Make current AI briefings aware of prior saved observations.
- Include last 14 days metrics/workouts and relevant saved observations in AI context.
- Add clear safeguards so old or dismissed observations are not overused.

Acceptance tests:
- Generate AI briefing.
- Confirm briefing is saved.
- Confirm observations are extracted and saved.
- Confirm saved observations appear in Lab history.
- Confirm dismissing an observation hides it from active list.
- Confirm future briefing can access prior relevant observations.
- Run typecheck.

PHASE 2 — Persist onboarding state in DB

Current problem:
Onboarding completion lives in localStorage and is fragile.

Implement persistent onboarding state.

Create or extend onboarding state in DB:
- athlete_id / user_id
- onboarding_started_at
- onboarding_completed_at
- onboarding_version
- completed_steps json
- skipped_steps json
- current_step
- is_complete
- last_seen_at

Requirements:
- localStorage may be used only as temporary cache, not source of truth.
- When user logs in on another device, onboarding status must be correct.
- If onboarding is complete, it must not reappear.
- If incomplete, continue from correct step.
- Existing localStorage users should be migrated gracefully where possible.
- Do not break current onboarding UI.

Acceptance tests:
- New user starts onboarding.
- Progress persists after reload.
- Completion persists after logout/login.
- Completion works across device/browser simulation.
- Existing localStorage completion does not break.

PHASE 3 — Coach and parent relationship surfacing

Current problem:
coach_athlete_links and parent_athlete_links are written but not surfaced.

Build a simple v1 portal/read layer.

Coach v1:
- Coach can see linked athletes.
- Show athlete roster.
- Show basic readiness summary.
- Show upcoming training/race schedule.
- Show latest AI observations that are safe to share.
- Show link status: pending, accepted, expired, revoked.
- Do not build complex coaching tools yet.

Parent v1:
- Parent/guardian can see linked minor athlete.
- Show basic schedule.
- Show safety/recovery status.
- Show high-level wellbeing/readiness summary.
- Do not show sensitive performance/health detail unless explicitly allowed.
- Add placeholder for consent settings.

Relationship management:
- Athlete can see linked coach/parent.
- Athlete can revoke or request removal of link.
- Admin can view link status.
- Prevent orphaned relationships.
- Avoid duplicate invitation/link status concepts where possible.

Acceptance tests:
- Coach with linked athlete sees roster.
- Parent with linked athlete sees parent view.
- Athlete sees linked persons.
- Revoking a link removes visibility.
- Pending links are not treated as active.
